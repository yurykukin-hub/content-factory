# Тикеты: CF как хаб обращений экосистемы

Дата: 02.08.2026 · коммиты `49c44a7`, `c1d840f` · на прод НЕ выкачено

## Зачем это здесь

Обращения пользователей всех приложений (KB ERP, дальше НаWоде и Автосоюз) хранятся
в CF, а не в каждом приложении. Решение ADR `2026-07-ecosystem-health-architecture.md`
(03.07.2026): «хаб = CF, тикеты = таблица и модуль, не отдельный сервис». Причина —
здесь уже готово всё нужное: мультипроектность, ключи для машин, S3 под вложения,
MCP-сервер (стык с Claude Code для ночного разбора), Telegram-кнопки одобрения.

## Модель

`Ticket` (сквозной человеческий номер через `autoincrement`), `TicketAttachment`,
`TicketPlan` (план ночного агента в формате скилла `/autonomy` + критерии приёмки),
`TicketEvent` (append-only лента). Миграция `20260801214349_add_tickets`.

Статусы строками, как у `AutoPostTask`: `new → triaged → needs_info → planned →
approved → running → ready_to_deploy → deployed → closed`, вбок `rejected`,
`duplicate`, `waits_human`.

## API

- `POST /api/tickets` — приём; приложение представляется API-ключом, автор приезжает
  строковыми полями `reporter*` и пользователем CF **не заводится**.
- `GET /`, `GET /:id`, `PATCH /:id`, `POST /:id/comments`, `POST /:id/attachments`.
- Секция доступа `tickets` (добавлена в `shared/section-access.ts` и во фронтовое
  зеркало `src/composables/useSectionAccess.ts`).

## Безопасность — почему так строго

`body` и `context` тикета — **недоверенный ввод, который попадёт в промпт ночного
агента с доступом к коду**. Отсюда:

- контекст режется: 50 записей консоли, 20 запросов, 500 символов на запись, 64 КБ всего;
- суточный потолок 30 обращений на автора;
- вложение обязано соответствовать заявленному виду (`image` ≠ видео) — иначе в
  мультимодальный промпт приедет что угодно;
- потолок 10 вложений на тикет;
- смена статуса требует уровня `full`.

Приложение-источник дополнительно маскирует секреты в контексте до отправки.

## Область действия ключей — сделано 02.08.2026 (`a25f5af`)

`ApiKey.sectionAccess` — белый список разделов у самого ключа. Итог =
пересечение с правами владельца: **ключ только сужает, никогда не расширяет**.
Роль при заданном скоупе понижается до EDITOR, иначе ADMIN-байпас в
`resolveAccess` обнулил бы ограничения. Пустой скоуп = прежнее поведение
(существующий ключ MCP-сервера не тронут).

Для приёмника обращений выдавать ключ со скоупом `{ tickets: 'full' }` —
пресет «Только обращения» в Настройки → API-ключи. Пользователь-робот больше
не нужен.

## Осталось сделать

MCP-инструменты `cf_claim_tickets` / `cf_get_ticket` / `cf_post_ticket_plan` в
репозитории `content-factory-mcp` — без них ночной агент до тикетов не дотянется.
⚠️ В автономном профиле Claude Code сейчас разрешён весь MCP-сервер CF вместе с
публикацией в боевые каналы — ограничить списком трёх инструментов.
